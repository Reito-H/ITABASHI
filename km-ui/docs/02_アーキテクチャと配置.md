# 02. アーキテクチャと配置(Cloudflare Workers 案)

## 方針
- サーバー(km-operator)は一切変更しない。既存の `/kmx/api/v1` JSON API をそのまま使う
- 新UIは静的ファイル(HTML/JS)。ビルド不要、フレームワークなし(将来 React/Vue 化しても API 層はそのまま使える)
- ブラウザから見て UI と API を **同一オリジン** にする。これで CORS・Cookie の問題が消える

## 構成図
```
[オペレーターのブラウザ]
   │ https://km-ui.<自社ドメイン>/            … 新UI(静的アセット)
   │ https://km-ui.<自社ドメイン>/kmx/api/v1/… … API(プロキシ)
   │ https://km-ui.<自社ドメイン>/api/session   … ログイン情報(Worker が旧画面から抽出)
   ▼
[Cloudflare Worker  cloudflare-worker/src/index.js]
   │  /kmx/*  → そのまま転送(Cookie 往復、Set-Cookie の Domain 除去、Location 書換)
   │  /api/*  → Worker 内で処理
   │  それ以外 → [assets] = ../ui
   ▼
[https://km-operator.smartaxicenter.com/kmx/…]  (BIPROGY 運用、変更なし)
```

## ログインの流れ
1. 新UI(`/`)を開く → `live.js` が `/api/session` を叩く → 401 なら「ログインして実データに接続」リンクを表示
2. リンク先 `/kmx/HS/HSHS/HSHS0199.do`(旧ログイン画面がプロキシ越しに表示される)でログイン
   - 旧ログインは JS でフォーム送信している。送信先・フィールド名は DevTools の Network で確認し、新UI側にログインフォームを作るのが次の作業(03 参照)
3. オリジンが返す `Set-Cookie`(JSESSIONID 等)は Worker が `Domain` を外して返すため、`km-ui.<自社ドメイン>` に保存される
4. 以後 `/kmx/api/v1/*` は Cookie 付きで転送され、ログイン済みとして動く。`/api/session` が `operatorId` を返し、新UIが LIVE 接続に切り替わる

## 接続方式の切り替え(live.js)
| 方式 | 条件 | 用途 |
|---|---|---|
| A 同一オリジン直接 | `window.__KMX` が設定済み(`inject.js` が旧画面を置換) | 開発者が旧画面のコンソールから新UIを立ち上げる |
| B postMessage 中継 | `?proxy=1` で開き、ログイン済み km タブで `bridge.js` を実行 | サーバー・ドメイン一切なしの検証 |
| C リバースプロキシ | https で配信され `/api/session` が応答する(または `?live=1`) | **本番想定(Cloudflare Workers)** |
| mock | 上記いずれでもない | デザイン確認。架空データ |

## 書き込み API の扱い
- 現状は **読み取り専用**。`live.js` の `API.post` はトーストを出して何も送らない。Worker も `READ_ONLY="true"` で create/update/delete/send/confirm/dispatch_request/request_csv と POST(ログイン以外)を 403 にする
- 有効化の手順: (1) Worker の READ_ONLY を false (2) 旧 JS の `$cf.ajaxPost(... '/kmx/api/v1/tickets/create_ticket', payload)` を Network タブで観察して payload 構造を取る (3) `live.js` の `API.post` を実装 (4) 先に `create_temporary_ticket` 等の影響の小さいものから

## セキュリティ
- 顧客氏名・電話番号・住所が API 応答に含まれる。Worker のログに本文を出さない(`console.log(body)` 禁止)。`observability` はメタデータのみ
- Worker の前段に **Cloudflare Access**(Zero Trust)を置き、社内アカウントのみ許可する。暫定で `ALLOWED_IPS`
- `tickets/get_init_display_data` の応答に ZENRIN 鍵・CGI 鍵・無線回線パスワード等が入っている。新UIでは使わない項目は取り出さない。資料に貼らない
- Cookie は `Secure; HttpOnly`(オリジンの属性を維持)。`SameSite=None` は `Lax` に変更している
- 旧画面を Worker ドメインで表示するため `Content-Security-Policy` を落としている。新UIだけを配信する段階になったら Worker 側で CSP を再設定する
- テストアカウントの ID/パスワードはこの資料に書かない。別経路で共有

## ZENRIN 地図
- 旧UIは `zma_loader.js?auth=referer&key=<鍵>` を使う。Referer 認証なので、**自社ドメインから読む場合は ZENRIN 側で許可ドメインの追加が必要**(契約者=km 側/BIPROGY に依頼)
- 鍵は `get_init_display_data` 応答にあるため、新UIは同じ方法で取得して loader を読めばよい(ドメイン許可があれば)
- 許可が取れるまで、新UIの地図は Canvas の模式図(`map.js`)。座標変換は板橋営業所(35.7865,139.6835)原点の平面近似(`live.js` の `toXY/toLL`)。ZENRIN 化するときはこの 2 関数を地図 API の座標系に置き換えるだけで、範囲検索ロジックはそのまま使える

## デプロイ手順(Cloudflare)
```bash
cd cloudflare-worker
npm install
npx wrangler login
npx wrangler dev          # http://localhost:8787 でローカル確認(/kmx/* は本物のオリジンへ行くので注意)
npx wrangler deploy       # <name>.<account>.workers.dev に公開
```
独自ドメインにする場合は `wrangler.toml` の `routes` を有効化。Cloudflare Access を同じホスト名に設定。

## 代替案(参考)
- 共用レンタルサーバー(PHP のみ)ではプロキシ不可。PHP で cURL 転送を書くことはできるが Cookie と同時接続の扱いが面倒で非推奨
- 最終形は BIPROGY に新UIを `/kmx/ui/` 配下に置いてもらうこと。その場合 Worker は不要で、`live.js` は方式 A/C のどちらでも動く(`/api/session` がないため `window.__KMX` を旧画面同様にサーバー側で埋め込んでもらうか、`inject.js` の抽出ロジックを使う)
