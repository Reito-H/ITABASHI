# 01. 既存アプリの調査結果

対象: クラウド配車システム(km-operator) `https://km-operator.smartaxicenter.com/kmx/`
開発元表記: BIPROGY(画面フッター)。調査日: 2026-10-13。テストアカウント(板橋営業所)でログインして確認。

## 技術構成
| 層 | 内容 |
|---|---|
| 画面 | サーバーサイド生成 HTML(`HSHS9999.do?pageId=HSHSxxxx` の 1 エントリ + pageId で画面切替)。Struts 系の `.do` |
| フロント | jQuery 2.2.4 / jQuery UI 1.11.4 / Bootstrap 3 / Vue 1 系(`vue.js` 276KB、`ready:` フック使用)/ jquery.datetimepicker / simplePagination / SignalR 2.2.1(CTI 用)/ 自社共通 `cf-base.js`(`$cf.ajaxGet/ajaxPost`) |
| 地図 | ZENRIN zmaps API(`js.zmaps-api.com/zma_loader.js?auth=referer&key=...`)。Referer 認証。鍵は `tickets/get_init_display_data` 応答の `companyConfigAdmin` に含まれる(**鍵・パスワード類が応答に含まれるので、ログや引き継ぎ資料には絶対に貼らないこと**) |
| データ | すべて `/kmx/api/v1/<resource>/<action>` の JSON API。GET はクエリ、POST は JSON と思われる(`$cf.ajaxPost` 未検証) |
| セッション | Cookie(JSESSIONID 系)。`api/v1/SessionEnsure` で延長 |

結論: **サーバーを触らず画面だけ作り直す「フロント全面刷新」が可能**。既存 API をそのまま使う。

### 応答の共通形
`{ logMark: "<hash>", isSuccess: true, ...本体 }` / 失敗時 `{ msgs:[{type:"INVALID", code:"OSSCFL0002", msg:"...", path:"<項目名>"}], isSuccess:false }`
バリデーションエラーの `msg` が日本語で「必須」「書式」を教えてくれるので、未知 API はパラメータなしで叩いて必須項目を割り出せる。

### 確認済みのパラメータと応答(実際に呼んで確認)
**ticket_searches/search (GET)**
```
ticketNumber, operatorName, selectDate(1=配車日時,2=予約日時,3=受付日時), prearrangedSearchFlg(0/1),
dateFrom, dateTo ("yyyy/MM/dd HH:mm"), ticketType(1=即時,2=予約,3=即時と予約,4=問合せ,5=忘れ物; 0/6 は不正),
channelList, ticketStatusList (コード、空可), customerLastNameKana, customerFirstNameKana, customerPhoneNumber, customerPhoneNumber2,
passengerLastNameKana, passengerFirstNameKana, wirelessLineNumber, customerNumber, customerCompanyName, customerRankIdList, customerKindList,
departureAddress, bywayAddress, destinationAddress, selectProduct(0), packageIdList, reportNeeded(99), lineList, callingNumber, nonNotification(0),
trackingNeeded(99), throughNeeded(99), notSupposed(99), canceled(99), earlyReserved(99), reservedAutoDispatch(99), reservedFee(99), reservedConfirm(99),
dispatchDriverName, dispatchOperatorName, dispatchStatus(99), gradeList, colorList, makerList, carTypeList, occurrenceAtFrom, occurrenceAtTo, number,
qaDriverName, qaTargetList, qaTypeList, leftBehindTypeList, operatorId(必須。KMX_USER.operatorId), order(8), limit(100), pageNo(1)
```
応答: `{ allPageCount, allRowCount, pageNo, ticketDatas:[{ ticketNumber, channel, wirelessLineNumber, customerLastNameKana, customerFirstNameKana, passengerNameKana, receptionDate("yyyy-MM-dd HH:mm"), reservedDate, dispatchedAt, vehicleSize, dispatchedVehicles, operatorLastName, operatorFirstName, dispatchType("予約配車" 等), ticketStatus(日本語), customerPhoneNumber, customerPhoneNumber2, customersCompanyName, customerRankName, spUserId, spMemberFlag, webMemberFlag, departureAddress, destinationAddress, packageName, reportNeeded, line, callingNumber, throughNeeded, throughCompleted, reservedFee, reservedConfirm, dispatchDriverLastName, dispatchDriverFirstName, dispatchOperatorLastName, dispatchOperatorFirstName, dispatchStatus, carTypes(",ジャパンタクシー,"), colors(",2,"), reservedStartMinutes, departureBuildingName }] }`
0 件のときは `ticketDatas` キー自体がない。

**tickets/get**: `ticketNumber`, `operatorId`, `fromDisplay`(FLAG_OFF='0' で排他ロックしない)が必須。
**trip_infos/search (GET)**: `wirelessLineNumber`, `userName`(乗務員ログイン名), `date`("yyyy/MM/dd HH:mm" 必須)。応答: `{ driverName, wirelessLineNumber, shift("隔勤"), expectedCloseAt, tripCount, totalSales, attendanceId, tripInfoList:[{ tripStatusList:[{date,status}], onServiceAt, onServiceLatitude, onServiceLongitude, outServiceAt, outServiceLatitude, outServiceLongitude, distance(m), driveMin, fare, advance, fixedFare, meetCustomerFee, ticketNumber?, dispatchRequestId?, tripId, updateCount, ticketStatus?, customerFullNameKana?, passengerNameKana?, customerName? }] }`
**trip_infos/search_driver**: `lastNameKana`, `firstNameKana` → `driverInfoList`
**trip_infos/get_address**: `latitude`, `longitude` → `{ address }`
**running_paths/search (GET)**: `wirelessLineNumber`, `dateFrom`, `dateTo`("yyyy/MM/dd HH:mm"), `time`="1" → `runningPathList:[{ wirelessLineNumber, date("yyyy-MM-dd HH:mm:ss"), driver, office, status(車両ステータスコード), latitude, longitude }]`(約 5 秒間隔)
**running_paths/search_vehicle_status**: `dateFrom, dateTo, latitudeNorth, longitudeNorth, latitudeSouth, longitudeSouth`(範囲指定)
**map_vehicles/get_map_vehicle (GET)**: `northwestLat, northwestLon, southeastLat, southeastLon`(または `ticketNumber`)→ `vehiclePointList:[{ vehicleId, driverId, wirelessLineNumber, latitude, longitude, status, dispatchExcluded("0"/"1"), bearing, firstName, lastName }]`
**map_vehicles/get_vehicle_info**: `vehicleId` 必須
**map_searches/get_taxi_stand**: パラメータなし → `taxiStandList:[{ originalId, name, latitude, longitude, waitingVehicles, vehicleShortage(bool) }]`
**ticket_notices/get_*_count**: パラメータなし → `{ count:"0" }`。`get_waiting_ticket` / `get_prearranged_ticket` は `type` 必須。
**ticket_notices/get_tracking_needed**, **sos_accepts/check**, **get_unchecked_driver_message**: パラメータなし
**grade_types/search, colors/search, makers/search, car_types/search, offices/search, customer_ranks/search, product_types/search, system_types/search?type=N, products/search?pageLimit=&pageNo=&nonDetailFlag=1**: 一覧(`xxxList`)
**vehicles/search, drivers/search**: `searchKind`(一覧検索種別)必須。値は未確認。
**tickets/get_init_display_data**: `{ companyConfigAdmin, systemTypes, offices, approachPoints, dispatchDestinations, dispatchCondition, productForTickets, spAppAirlines }`(鍵情報を含む)

## 旧 UI の問題点(観察)
- 固定幅レイアウト(1280px 以下で横スクロール)。ログイン画面も右にはみ出す
- 日付範囲は 2 つのテキスト入力 + jQuery datetimepicker。プリセットなし
- 検索条件は巨大なダイアログ(チェックボックス 40 個超)。ステータスの意味が色で表現されていない
- 伝票検索結果は固定テーブル(`jquery.tablefix`)。ソートはサーバー `order` のみ
- 主要機能の多くがタブ/折りたたみ/ダイアログの奥にあり、画面上から存在がわからない
- 通知ポーリングが 10 本以上の API を数秒おきに叩く(ネットワークタブで同じ API が 3 回ずつ連続)
- ZENRIN 読み込み失敗時に `ctlib.js` で未定義参照エラーが多発(コンソール)
